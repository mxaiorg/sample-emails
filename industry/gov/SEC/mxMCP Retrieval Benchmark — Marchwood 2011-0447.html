What the Benchmark Tests

The Premise

The corpus models an enforcement matter in which a decisive written commitment was made in 2011, lost from both parties' document systems in a 2016 platform migration, and became the difference between a $4.3M action collapsing and a $2.15M settlement fourteen years later. Every person who negotiated it had left. The email archive was the only surviving witness.

Why the Decoys Matter More Than the Volume

Bulk filler makes the haystack a haystack, but it does not compete for top-k results. The evaluation is won or lost on the ~155 hand-built hard negatives: same document numbers, same vocabulary, wrong entity. Finding the needle in a pile of unrelated mail proves very little; finding it while declining four near-identical look-alikes is the actual claim.

The Three Scoring Axes

Each query is scored 0–2 on recall (did it find the right documents), precision (did it avoid the decoys), and verdict (was the final answer correct). Four queries × three axes × two points = 24 available. A demo passes only when the primary query scores full on all three.

Key Findings

The disambiguation disclosure is load-bearing

Two entirely separate matters share a file number by design. On the bare-number query the connector volunteered the ambiguity before any answer was drafted — naming both counterparties and warning that the identifier is unique only within the office that issued it. An agent that ignores that disclosure silently merges the two matters and fails precision. This behaviour, not ranking quality, is what carried the hardest query.

A recovery channel prevented a recall miss

One message in the target sequence never ranked into any result set across all eight searches. It was named in the connector's missingRelated field and retrieved directly by identifier. Without that channel the third query would have returned 11 of 12 documents and scored partial on recall.

Retrieval degrades sharply without identifier pinning

A control search was deliberately issued without the Pin parameter. It returned 50 messages, of which 48 were near-identical bulk correspondence; the two relevant results survived only because the date filter happened to be narrow. The same question with Pin set returns the answer at rank 1.

Transport size limits can truncate evidence

On two searches the connector dropped attachment text or reduced messages to header-only stubs to fit response size limits, disclosing each truncation explicitly. No scored item was affected in this run, but on a query whose answer depended on a truncated body, a second fetch would have been required.

Engineering Actions

Enforce identifier pinning in agent configuration
HIGH PRIORITY
The Pin parameter is the single largest determinant of retrieval quality observed in this run. Left to model discretion it will sometimes be omitted, and when it is, results are dominated by vocabulary-proximate bulk traffic. Consider making it non-optional whenever a query contains a document, matter or case identifier, and carrying it forward automatically on follow-up searches within a conversation.
Instrument the missingRelated recovery path
RECOMMENDED
One required document never ranked into any result set but was recovered because the connector disclosed it as thread-related. This channel converted a partial recall score into a full one. Worth confirming that agents reliably act on missingRelated rather than treating a result set as complete, and worth measuring how often it is the sole path to a required document.
Review transport size-limit behaviour
MONITOR
Two searches dropped attachment text or reduced messages to header-only stubs to fit response limits. The connector disclosed each truncation, which is the right behaviour, but a query whose answer sits inside a truncated body would require a second fetch that an agent may not know to make. Consider whether the truncation notice should be more directive.

Benchmark Maintenance

Investigate two bonus items that did not surface
LOW IMPACT
Two supporting messages — the numbering-scheme notice that explains the file-number collision, and the message where the 2013 precedent re-surfaces from the archive index — did not rank in this run. Neither is scored as required and neither affected the outcome, but both are useful demo colour. Worth checking whether they are reachable with different phrasing or genuinely under-ranked.
Preserve the deliberate in-world miscount
NO ACTION
One message describes the recovered sequence as eleven documents where the production index correctly lists twelve. This is intentional — real productions contain human miscounts — and an evaluator that notices it is behaving correctly. It was caught in this run. Do not 'fix' it.
Re-run before each customer demo
ONGOING
This is the third independent run. Scoring the same four queries before a live demo gives an objective pass/fail gate rather than a subjective impression, and detects regressions in ranking behaviour that would otherwise surface in front of a prospect.

Key Strategic Insights

The claim is now falsifiable, which is the point

The commercial argument — that an email archive answers questions a system of record gets wrong — is easy to assert and hard to prove. This benchmark converts it into a score with a defined pass condition. A prospect's technical evaluator can be handed the grading key and told to check the work.

The demo is won on the decoys, not the volume

Bulk filler supplies a realistic denominator but does not compete for top results. Every decisive moment in this run turned on declining a near-identical look-alike: a letter two days earlier that expired, a second matter with the same number, a firm with the same name. Effort in corpus construction should stay concentrated there.

Self-disclosure beat ranking on the hardest query

On the query designed to force a collision, what saved the answer was not that the right documents ranked higher — it was that the connector volunteered the ambiguity in its own response metadata before an answer was drafted. This is a differentiating behaviour and is worth surfacing explicitly in demos rather than leaving it as background.

One dependency sits between this result and a bad demo

The Pin parameter. With it, the answer is at rank 1. Without it, 96% of a result set was noise. A live demo driven by an agent that omits it on one question will look materially worse than this scorecard suggests. This is a configuration risk, not a retrieval-quality risk, and it is cheap to close.
